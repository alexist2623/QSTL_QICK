## Findings passed to the parent/RTL worker

1. **Fine GUI input correspondence is narrower than the full RF specification.** `fine/prepare.py:229` compares requested versus returned GUI duration and sweep axes, but does not explicitly compare static gain/frequency/phase/channel or the number of pulse events before using `actual` runtime specs as the width oracle input at line 256. Thus this suite alone cannot detect a GUI transformation of those un-compared values. Saved `gui_input.json` and `gui_runtime_specs.json` permit an independent correspondence check; existing software regression coverage should not be described as that missing assertion.

2. **Fine configuration provenance is incomplete in its prepared artifact.** `fine/prepare.py:102` records GUI/library Python hashes, but the inspected `prepared.json` does not directly preserve the final configured soccfg, baseline `soccfg.json` hash, candidate HWH hash, `extension_v5.py` hash, or actual sum-v2 source hash. Template/project-file hashes and the namespaced SG-v6 source comparisons are present. General-suite preparation additionally records HWH/helper hashes and `v5_route_metadata.json`. Any supplement should be a separately identified evidence file, without rewriting the original preparation record or claiming it was captured earlier.

3. **Fine and exact-HOLD physical coverage must be stated precisely.** `fine/harness.py:83` records RF/AWG inputs and sum output, but not the final output-slice data. Its per-lane delayed sum oracle does validate v5 sum behavior; the fine RF width itself is measured at the sum input. The final-slice oracle exists in the separate general/HOLD suite. Do not describe the fine-only result as a direct analog or final-RFDC measurement.

4. **Exact-HOLD timing labels need the anchor qualification.** `extension_v5.py:105–106` computes `awg_hold_physical_start` from command+44 and records `requested_timing_error_cycles=0`. That AWG component time is inferred, while the summed physical slice is independently checked. The zero error is relative to the compiled HOLD anchor with an explicitly requested +100 ns RF offset. Existing RAMP startup seven clocks and guard one clock remain exposed. This is not proof of the ideal zero-offset four-segment timeline or simultaneous shared-port output.

## Same-timestamp diagnostic

The production GUI negative test retains the shared-port spacing guard and preserves eight exact zero-offset requests. The separate low-level `raw_same_timestamp.py` deliberately bypasses GUI construction to measure serialization; it does not relax the GUI guard.

The executed fine runner imports `fine/raw_report_v2.py`, whose report uses `diagnostic_only=true` and `inferred_physical_*` fields. It computes `simultaneous_output_supported` from measured input-edge skew plus independently checked downstream delays. Its `passed=true` means the diagnostic completed, not that simultaneous timing is supported. Final reporting must retain that distinction and report the actual skew. The older preparation module’s checker uses less explicit physical field names; it is not the checker selected by `fine/run.py`.

No additional implementation defect was found in the paired-HWH/latency contract during this review. The findings above concern proof coverage/provenance and precise reporting, and were forwarded while the RTL worker was still active.
